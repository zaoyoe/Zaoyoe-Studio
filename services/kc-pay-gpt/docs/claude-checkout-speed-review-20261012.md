# Claude 充值速度与稳定性审查（2026-10-12）

本文件记录改造前的审查证据；后续已按用户要求实施优化，修改与验证结果见 [实施记录](claude-checkout-speed-change-20261012.md)。下文行号与行为描述对应审查时版本。

审查范围：本地 KC 系统当前 Claude 原生结账路径及用户提供的几次日志。用户已明确，人机验证操作是故意延长的测试，银行卡也是必然拒付的测试卡。因此不把人工验证时长、测试卡拒付或总任务时长作为性能瓶颈，也不分析测试卡拒付原因。本次只做代码与日志审查，没有修改支付逻辑，没有发起真实支付。

## 1. 结论

存在明确的提速空间，主要在页面就绪与套餐选择，实际填卡和地址已经很快。问题是旧的探测与控制方式混杂，而非 Playwright 版本过旧。

- 确认有一处等待选择器在已渲染的测试页面上仍耗尽 6 秒超时，可以首先消除。
- 套餐选择有两套逻辑，前一套可能在页面未完成渲染时逐个等候选元素，后一套又重新点击和读金额。
- 应把固定睡眠替换为明确的页面、套餐、金额和 Stripe iframe 就绪条件，同时修正提交前金额可能沿用旧值的问题。
- 提交后应统一状态观测，避免两段重复扫描、重复等待，以及只凭离开升级路由就判成功。
- 必须保留提交事实和未知结果保护，不能为了速度扩大自动重试范围。

已证明的收益是消除约 6 秒无效等待。综合重复套餐探测与固定等待，提交前减少约 10–20 秒是工程估计，需在相同代理和测试账号条件下重新测量，不能作为承诺。

## 3. 最优先：统一套餐确认，并消除错误等待

### 3.1 已确认的 6 秒无效等待

位置：`stripe-payment.js:399` 的 `ensureClaudePlanSelection`，等待语句位于第 408 行。

```js
page.waitForSelector(
  'text="Pro 按月计费", text="设置您的套餐", input[type="radio"], [role="radio"]',
  { timeout: 6000 }
).catch(() => {});
```

这里把 Playwright 的 `text=` 选择器与 CSS 候选混在一条逗号表达式中，不能正确表示任一候选就绪。在已经展示月费文字和单选框的本地 Playwright 页面上，旧表达式仍在约 6000 毫秒后超时；合法的单选框 Locator 在约 8 毫秒后返回。8 毫秒是离线测试值，不代表线上页面加载速度。

日志也吻合：最近两次从后续套餐核验开始，到第一次打印应付金额，均正好间隔 6 秒。应使用明确的 Locator 及就绪状态，不能简单缩短超时来掩盖定位问题。

### 3.2 两套套餐控制逻辑重复工作

位置：`pricing-checkout-claude.js:7` 的 `ensureClaudeInterval`、第 135 行的 `ensureClaudeCheckoutTier`、第 278 行调用；随后 `stripe-payment.js:1191` 又调用 `ensureClaudePlanSelection`。

- 第一套月费回退逐个等待 5 个候选，每个最多 1500 毫秒；若均未找到，合计约 7.5 秒。几次日志的这一阶段稳定在 7–8 秒，且没有成功切换的日志，和该回退路径相符。这是强线索，尚不能把全部 8 秒都归因于它，需要补充候选耗时与页面就绪日志确认。
- 原生结账就绪主要由 `/upgrade/pro` 或 `/upgrade/max` URL 判断，页面可能仍未完成渲染或 React 事件绑定。
- 第二套即使 Locator 已点击，仍继续执行原生 DOM 点击，并尝试点击父容器。一次操作可能实际触发多次点击，引起额外渲染或 Stripe iframe 更新；这属于代码风险，日志不能证明每次都发生了 iframe 重挂载。
- 第二套使用每 800 毫秒检查一次金额；完成后又固定等待 1500 毫秒。

建议用一个 Claude 套餐控制器完成选择：读取明确的产品和计费周期；确认交互已就绪；只在不匹配时执行一次正常点击；等待选中状态、应付金额和当前 Stripe iframe 同时稳定。选择完成后仍保留提交前的独立复核，这一复核不能被“合并逻辑”省略。

## 4. 提速时必须一起修正的金额保护

位置：`stripe-payment.js:784` 的 `readCheckoutDueAmount`，第 1074 行的 `captureCheckoutDueAmount`，第 1387 行的提交前检查。

- 金额读取依赖整个 body 的 `textContent` 和有限的文案正则，不能保证读的是当前可见的应付摘要。离线测试中 `Due today USD20` 可识别，`Total USD20`、`应付金额 USD20` 不能识别。因此日志中的“未知”可能是未加载，也可能是文案未匹配，需要 DOM 证据区分。
- `captureCheckoutDueAmount` 收到已有正金额后直接返回，未重新读取页面。离线复现：页面当前应付 USD200，传入旧的 USD20，结果仍为 USD20。因此“提交前确认应付”日志不一定代表提交前的最新金额。
- 月费确认使用正金额不超过 35 的宽泛判断，不检查币种；金额始终未知时也可能结束核验而未阻止提交。
- 年费和 Max 的验证不完整：这套后续逻辑将 `/upgrade/*` 都按 Pro 月费或年费处理，Max USD100 可能被当作错误年费而阻断。

建议为 Pro 月付、Pro 年付、Max 5x、Max 20x 建立明确的产品、周期、币种和金额规则；提交前重新读取当前可见汇总，核对实际选中套餐。税费、折扣或补差价只有在业务规则明确支持时才能接受。金额或套餐证据缺失、币种错误、金额超出允许范围时停止提交，不能沿用旧金额或推测金额。

## 5. 更合理的提交后逻辑：统一状态观测

位置：`stripe-payment.js:1549` 的 `handlePostSubmitPhase`、第 1759 行的 `waitForPaymentResult`。

现有日志称为“并行等待”，实际上每轮顺序执行拒付扫描、字段错误扫描、验证码扫描和 URL 判断，再睡眠 500 毫秒；后面的支付结果循环又重复扫描并等待 2 秒。如果没有验证码，而且成功提示仍在原生升级页上，第一阶段可能先走完最多 45 秒等待才进入结果检测。当前测试没有证实这一最坏路径。

改进方向：在点击提交前建立同一个支付状态观测器，监听官方页面响应、导航、iframe 生命周期和可见状态变化，用事件唤醒检查，保留有界的低频轮询兜底。统一处理“处理中、需要验证、明确失败、明确成功、结果未知”，共享一个截止时间并清理监听器。

现有 Claude 代码已经有捕获 Stripe 结账链接的 response 监听，但覆盖范围不是完整支付状态。`pricing-checkout.js:1191` 的 ChatGPT 结账观测器已有请求失败、响应错误和弹窗追踪，可提取公共生命周期；它的路径和域名匹配限定 ChatGPT，不能直接用于 Claude。

安全约束：

- 继续通过官方 UI 提交支付；监听官方响应是读取现有流程，不是自行调用私有扣款接口。
- 只离开 `/upgrade` 不能证明支付成功，登录跳转或错误页也可能离开该路由。应结合明确的官方支付结果或目标订阅权益确认。
- 避免将整页默认元素超时提高到 180 秒；状态等待期限与单次 DOM 读取期限应分开。
- 周期性调试截图不要阻塞主要状态检查，保留最终结果截图；截图工作应有界并避免并发堆积。

## 6. 登录和账号探测：合同不一致，元数据不应挡住关键路径

位置：`claude-auth.js:79` 的 `fetchClaudeAccount`、第 198 行的 `bootstrapClaudeSession`。

直达升级页、使用 `domcontentloaded` 已经实现，不需要重写成先打开聊天主页。需要改的是后续判定：当前主要根据路由及页面没有特定错误就打印“登录有效”，之后还单独执行 `fetch('/api/auth/current_account')`，请求没有显式的可取消超时。

最近两次登录状态日志到继续结账均间隔 2 秒，额外账号请求是值得测量的候选，不能把全部 2 秒都确定归因于它。推荐在导航前被动监听页面本来就会发起的账号或组织引导响应，将身份确认与结账就绪关联。必要元数据在填表前到位；仅用于展示的元数据有界获取，不阻塞关键路径。

另一套 Axios 探测调用 `api.claude.ai/api/auth/current_account`，没有应用文档中的代理选项，网络失败后还可能仅因 sessionKey 格式符合而返回 `ok:true`。这和浏览器内的账号探测路径、语义不一致，应区分“格式可解析”和“在线身份已确认”。没有现场 HTTP 证据，不能断言该端点已经废弃；应先验证路径有效性，并保持与支付浏览器相同的授权会话和代理出口。

## 7. 人机验证：不作为此次速度瓶颈

人工测试耗时已排除。现有交互已包含题目材料就绪检查、帧版本保护、过期操作拒绝、截止时间和拖动题换题，不能为了提速删除这些机制。

后续可改进的是状态回传及时性：前端动作经 WebSocket 到本地服务，浏览器 worker 通过 HTTP 长轮询取动作。长轮询收到用户动作时会立即返回，不意味着一次点击要等 30 秒；但无动作期间，worker 等待可能妨碍及时发现页面自行完成验证或发生其他状态变化。可使用事件通知或可取消的竞争等待唤醒页面检查。

日志 `未完整就绪（grid_ready，已加载9/9）` 也不等于图片明明加载完成却判断坏了：当前就绪检查要求连续两次稳定，截止时可能只完成一次。应细分为材料加载与等待稳定的原因，帮助后续诊断。本项不用于估算本轮提速收益。

## 8. 支付结果未知时保留提交事实

位置：`payment-retry.js:185–208` 的分类输入，以及第 262 行起的未知结果保护。

当前验证码、超时等非卡片错误会强制把 `submitted`、`submissionAttempted` 和此前已记录的 started 状态当作未提交。已有的未知结果隔离机制可能因此无法发挥作用。仅凭验证码或超时关键词，不能确定官方从未收到支付请求。

应将“已尝试提交”作为不可抹除的事实，区分验证中、明确未扣款失败、已成功和未知。只有明确失败证据才允许重新提交或换卡；结果未知保持人工复核。页面提示重新验证时，也不能只凭模糊文案重新点击支付。

这是代码层面的安全缺口，不代表测试日志发生了真实重复扣款；用户的测试卡拒付仍完全排除在原因分析之外。

## 9. 实施顺序与验证范围

1. 修复错误的 6 秒选择器；统一套餐选择与就绪判定；同时实现提交前新鲜金额、产品、周期和币种检查。
2. 统一支付状态观测；修正成功依据和未知结果保护，验证只提交一次。
3. 收敛账号探测，必要元数据有界获取；改进 worker 事件唤醒和阶段诊断。

验证应使用本地页面夹具及沙盒覆盖：延迟渲染、事件绑定尚未完成、Stripe iframe 重挂载、已选中目标套餐、切换后金额更新；Pro 月付/年付与 Max 5x/20x；币种错误、金额缺失、旧金额与当前金额不同；延迟验证码、同页成功、登录跳转、明确失败、结果未知及关闭页面。禁止通过缩短安全等待或自动重复提交获得表面上的加速。

上线或本地应用后补充单调时钟分段指标：导航、账号确认、套餐就绪、选择生效、iframe 就绪、表单填写、提交前复核、提交动作、官方状态响应、人工验证等待。人工时间单独统计，比较相同条件下的中位数和高分位耗时，而非只看单次总时间。
