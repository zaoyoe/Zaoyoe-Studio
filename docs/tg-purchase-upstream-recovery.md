# TG 原上游订单恢复与未受理凭据结案

2026-10-17。适用于“已付款、原履约请求已提交，但结果进入人工复核或失败”的购买单。
本功能为增量实现；迁移由操作者手动执行。代码测试、结构检查、数据库并发验收和真实业务验收分别记录。

## 安装顺序

前置为已经完成的 TG runtime reconciliation、支付/履约复核与 purchase review resolution。
若 `fn_tg_purchase_resolution_ready()` 未就绪，应先按
`docs/tg-preview-reconciliation-20261017.md` 中的恢复流程排查；不要用旧迁移覆盖现有函数。

在前置就绪后，依次手动执行：

1. `supabase/migrations/20261017_tg_purchase_upstream_recovery.sql`：增加原上游单归属索引、不可变恢复凭据表和仅 service-role 可调用的事务 RPC。
2. `supabase/migrations/20261017_verify_tg_purchase_upstream_recovery.sql`：只读检查 readiness、权限、锁、版本、原请求关联和凭据保护。

第二份预期输出：

```text
TG upstream recovery structural checks passed; concurrent/business acceptance remains NOT RUN
```

这代表结构检查通过。它不代表真实订单已补录、已关闭、已退款，或数据库并发验收完成。
第一份迁移不处理现有订单；若已有上游单号归属冲突，唯一索引创建会中止整个事务，须先核对冲突来源。
Codex 不执行 SQL。安装后刷新管理页；前置未生效时，入口显示迁移待执行，不开放提交。

## 公共前置与入口

进入 TG 管理页 → 购买订单 → 详情 / 处理 → 原上游订单恢复 →
“补录原上游单 / 查看结案凭据”。当前详情弹窗内完成核验、提交和记录查看。

服务端要求：购买单 `payment_status=paid` 且有 `paid_at`、未关闭/取消；
原任务来源为本次购买，接收人、产品和权益一致，已保存原提交时间、提交标识、提交币种及至少一次尝试；
任务为 `manual_review` 或 `failed`，且无工作租约。支付仍为 `manual_review` 的订单须先走原支付审核。
不能用当前币种配置或余额推测历史提交币种，也不能手动清空提交标记来取得资格。

两个动作都携带购买与原任务的 `updated_at`。服务端核验后，事务按购买单 → 原任务加锁，
再次检查版本、租约、状态与权益。版本变化时刷新详情重新核验，不覆盖原任务。

## 路径一：补录并核验原上游订单

1. 从原提交日志或上游工单取得本次请求的原 Gramix UUID；不能仅凭相同用户名、数量、金额或相近时间选择订单。
2. 选择“补录原上游订单”，填写 UUID，点击“核验原上游订单”。这是只读核验。
3. 服务端独立 GET 该单，验证原提交标识、接收人、产品、期限/Stars 数量、历史扣款币种、API 来源和状态，并检查未被其他本地任务占用。
4. 查看核验结果，填写 6–500 字处理原因，确认针对本次原始提交，再点击“确认补录原上游订单”。
5. 确认请求会再次 GET 上游；事务将上游 ID 关联到原任务，并在同一事务留存恢复凭据及审计。

这条恢复路径比已有可信上游 ID 的普通轮询更严格：GET 必须明确返回与原任务一致的
`idempotencyKey`。上游未返回关联标识时，即使其他字段相同也不能补录。
应让上游提供可核验的原订单；不能拿同一用户的其他成功订单代替。

| 上游核验状态 | 本地结果 | 后续动作 |
| --- | --- | --- |
| completed | succeeded / 已发货 | 记录原单完成；不重新购买 |
| created、processing | retry_waiting | worker 后续只轮询已保存的原单，不再次 buy |
| failed、canceled | failed | 保留原单，可继续按已有关闭条件核验处理；不自动重发 |
| 原标识缺失、字段不符、归属冲突或查询失败 | 拒绝补录 | 原状态和提交记录保留，继续核查 |

Stars 数量只接受现有上游协议中的 `extraData.quantityStars`；顶层 quantity/stars 不作为权益凭据。
补录不会重置原提交标识、`submitted_at`、`attempt_count`，不会删除历史尝试或生成新任务。

## 路径二：登记上游明确未受理凭据后结案

仅适用于原任务尚无已关联上游 ID 的场景。已经找到原单时先走路径一；
上游仍可能发货时继续冻结，不能用结案代替对原单的核实。

1. 取得上游针对本次原请求的明确答复：**未受理、未发货，且不会后续发货**。
2. 在受控位置留存原始答复/日志。页面登记其工单编号、原请求日志编号或可回查的留档位置；本页面不上传或自动认证附件。
3. 选择“登记未受理凭据”，填写来源（客服/工单或原请求明确拒绝记录）、凭据编号/位置、上游确认时间、20–1000 字答复摘要，以及 6–500 字结案原因。
4. 点击“核验原任务与结案条件”。服务端只读反查原提交，排除已知矛盾上游单。
5. 勾选四项确认：针对原请求、上游明确未受理且不会发货、已核实未发货、已核对收款/退款处理方式。
6. 点击“登记凭据并关闭订单”。服务端再次反查，事务原子保存凭据、取消原任务、记录 `closed_at/closed_by/close_note` 和审计。
7. 只有收到同一订单、有效关闭时间和 `closed` 结果后，页面显示“订单已关闭”。按已核对的方案另行处理支付渠道退款，并留档退款结果。

凭据明确标注为 `operator_attestation`（管理员人工核实），不伪称上游 API 已自动证明未受理。
确认时间不得早于原提交或晚于当前时间；摘要须明确关联原请求，不录入密钥、支付凭证或客户查询口令。

反向查询必须完整结束、无缺失关联标识、无匹配或矛盾订单。当前最多查询 3 页、每页 100 条；
返回 search_limited、submission_unknown、missing_correlation、mismatch、unavailable 或超时时均拒绝结案。
完整空结果也只用于排除矛盾，不能代替明确未受理凭据。当前余额、一般性报错和超时不构成该凭据。

结案保留 `payment_status`、`paid_at`、原提交币种、原提交标识、提交时间和尝试历史。
**关闭不是退款，也不会自动重买、补发或解冻。** 用户查询和后台列表应显示已关闭，收款事实仍为已付款。

## 结果不明、并发与记录

操作使用浏览器生成的 UUID、请求摘要和操作者绑定。响应丢失后，保持同一内容再次确认，
会复用原操作编号；已提交的相同操作返回原事务结果，不再次写凭据或购买。
修改表单会使原预览失效，并产生新的操作编号。若已经刷新/离开页面，先查看详情与恢复记录确认结果。

恢复记录按时间显示：操作者、动作、原上游 ID、原因、凭据来源/编号/摘要/确认时间和结果。
记录只追加，不允许普通用户读取，也不向浏览器输出原提交标识、请求摘要或原始上游 payload。
发生版本冲突、任务重新运行、归属冲突或上游不一致时，不得绕过保护；刷新并核对历史。

| 管理接口 | 行为 |
| --- | --- |
| GET `/api/admin/tg/purchases?order_no=TGP-...&recovery=1` | 只读恢复资格、迁移状态和最近 20 条记录 |
| POST `inspect_upstream_order` / `inspect_nonacceptance` | 管理员只读核验；仍执行同源和 JSON 检查 |
| POST `link_upstream_order` / `close_with_nonacceptance` | 超级管理员、可信 Origin、严格字段、两个版本、重新查单及事务落档 |

## 验收与发布边界

| 项目 | 本轮状态 |
| --- | --- |
| 服务、接口、页面与 SQL 源码契约测试 | 见 `docs/tg-preview-reconciliation-20261017.md` 本轮追加记录 |
| 增量迁移实际执行与只读数据库结构核验 | NOT RUN，留给操作者 |
| 原单 completed/processing/failed 的真实恢复 | NOT RUN，须在获准的受控订单验证 |
| 明确未受理凭据真实结案、用户状态与退款核对 | NOT RUN |
| worker 并发、双管理员并发、归属竞争及数据库事务回滚 | NOT RUN；自动化隔离测试不替代数据库并发验收 |
| 真实支付、退款、补发与生产发布 | NOT RUN |

数据库验收需分别验证：核验后版本变化拒绝、worker 租约冲突拒绝、两个任务抢同一上游 ID 仅一个成功、
同操作并发重试仅一条凭据、错误请求重用 operation UUID 拒绝，以及证据/审计失败时状态更新全部回滚。
保留每个真实场景的订单、操作者、时间、返回结果与受控留档位置后，才能将其从 NOT RUN 改为实际结果。

API、恢复服务和 readiness 属于 KVM4 Verify Server；管理静态页属于 Vercel；增量 SQL 由数据库操作者执行。
后续发布仍按 AGENTS.md 从最新 main 发布同一提交；此次代码更新不执行 SQL、不启动 worker、不修改商品开关。
