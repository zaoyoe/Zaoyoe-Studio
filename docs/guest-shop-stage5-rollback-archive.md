## 3. 历史订单和未付款订单边界

- 历史已付款订单：商品入口关闭不应改写订单、支付或履约状态；继续履约或退款必须沿用 `docs/guest-shop-payment-fulfillment-runbook.md`。本次演练没有重新操作历史已付款订单，因此不把“继续履约/退款”登记为本次新增实测结论。
- 已存在的未付款订单：本归档不自动取消、不代用户支付，也不声明 provider 订单已失效；运营人员按现有运行手册查询、过期、释放或人工处置。
- 新游客订单：只要该精确 product/SKU 仍关闭，preview/create 必须拒绝，不能生成新订单、支付意图或库存预占。
- 本归档不保存订单号明文；若需要关联生产订单，只能在受控运营系统保存脱敏引用。

## 4. 幂等、脱敏与审计合同

- 幂等键固定为归档记录 ID。同一键和同一规范化内容重复归档时返回同一记录，不追加重复事件；同一键但内容不同必须报冲突。
- 必填审计字段：schema version、记录 ID、环境、日期、精确 product/SKU、开关前后状态、证据来源、观察错误码、订单边界、责任角色和重新启用条件。
- 仓库不得保存邮箱、查询密码、claim token/secret、取货口令、卡密/库存内容、二维码/checkout URL、支付密钥、provider secret、原始 webhook body 或支付响应正文。
- `tests/guest-shop-stage5-archive.test.js` 校验精确范围、关闭状态、生产错误码、重复归档幂等、冲突拒绝以及敏感字段 fail-closed。

## 5. 责任人与重新启用条件

| 责任 | 角色 |
| --- | --- |
| 归档与商品开关 | 商品开关负责人 |
| 历史支付、退款和未付款异常 | 支付/退款负责人 |

重新启用前必须同时满足：重新执行 Task 2.1 §61.9.2 的精确 product/SKU review；确认生产发布及适用运行门禁；获得用户明确批准。部署成功、历史测试通过或本归档完成都不是重新启用授权。
