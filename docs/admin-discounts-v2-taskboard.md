## 1. 当前状态（2026-04-09）

按当前代码状态看，优惠券码已经不是简单 CRUD，而是一个具备交易校验、风控联动、后台审计与恢复审批的 V1 系统：

- 交易侧已经支持：
  - 站点限制
  - 商品 / 分类 scope
  - 每用户限次
  - 禁止 0 元单
  - 预校验与正式下单双入口
- 风控侧已经支持：
  - 风险命中后自动停用优惠券
  - 后台恢复审批
  - 批量恢复跑次审计
  - 风险 case 联动
- Admin Studio 已经支持：
  - 列表、详情、编辑
  - 恢复审批
  - 批量恢复与历史跑次
  - 最近使用与风险摘要

但从产品收口角度看，当前仍有 4 个关键断点：

1. 生命周期不完整：只有 `is_active` / `expires_at`，没有 `starts_at` 和完整状态语义。
2. 风控闭环不完整：只有自动停用，没有自动恢复、观察期或恢复策略。
3. 历史真相不完整：券规则可改，但订单侧缺少稳定的优惠快照。
4. 增长能力不完整：当前更偏“防亏损工具”，还不是“营销资产系统”。

## 2. V2 的阶段目标

V2 不追求一步到位，而是按下面顺序推进：

1. `P0` 先把“状态、真相、闭环”收住
2. `P1` 再把“用户资产化、经营分析”做起来
3. `P2` 最后再做“营销资产中心、规则平台化”

## 3. 阶段完成标准

### P0 完成标准

满足以下条件，才算 P0 完成：

1. 优惠券支持 `starts_at`，可提前配置并自动生效
2. 优惠券有明确主状态，而不再只是布尔开关
3. 风控停用后的券具备可解释的恢复路径
4. 任意成功订单都能回溯到当时真实生效的优惠规则
5. 退款后，次数、每用户额度、经营统计口径一致
6. Admin Studio 能直接展示“当前状态 / 原因 / 最近动作 / 建议动作”

### P1 完成标准

满足以下条件，才算 P1 完成：

1. 用户可以在结算时直接查看并选择可用券
2. 系统支持公开领券与定向发券
3. 后台能看到优惠券的发放、领取、尝试、核销、退款漏斗
4. 后台能看到单券让利、实付收入和新客转化贡献
5. 运营可按站点 / 人群 / 渠道做投放与分析

### P2 完成标准

满足以下条件，才算 P2 完成：

1. 运营视角可以统一看优惠券、兑换码、权益资产
2. 新增营销规则不再高度依赖底层交易函数改造
3. 能通过编排策略完成预热、生效、恢复、归档和复盘

## 4. 分阶段建议

建议主线按下面三期推进：

- `Phase 0`：优惠券状态与结算真相收口
- `Phase 1`：优惠券资产化与经营分析
- `Phase 2`：营销资产中心与规则平台化

如果需要分支管理，建议主分支使用：

- `codex/admin-discounts-v2-phase0`
- `codex/admin-discounts-v2-phase1`
- `codex/admin-discounts-v2-phase2`

## 6. 任务明细

## `DV2-0-1` 优惠券状态机与时间生命周期设计

目标：

- 把优惠券从“布尔开关”升级成“有完整状态语义的业务对象”
- 支持预热、生效、停用、风控停用、过期等完整生命周期

涉及范围：

- `discount_codes` 语义重构
- Admin Studio 列表 / 详情状态文案
- 运营配置表单

要做的事：

1. 明确状态集合：
   - `scheduled`
   - `active`
   - `paused_manual`
   - `paused_risk`
   - `expired`
   - `archived`
2. 定义关键字段语义：
   - `starts_at`
   - `expires_at`
   - `lifecycle_status`
   - `status_reason`
3. 明确状态流转规则：
   - 到点自动生效
   - 到期自动失效
   - 风控停用与人工停用分离
4. 明确“是否允许直接编辑已使用券”的产品策略

验收标准：

- 运营能提前配置未来生效时间
- 后台任意一张券都能落入唯一主状态
- 页面展示状态和实际结算逻辑一致

## `DV2-0-2` 订单优惠快照与版本语义收口

目标：

- 解决“券规则被修改后历史订单失真”的问题
- 为后续 ROI、漏斗、客服解释打基础

涉及范围：

- 下单链路
- 优惠预校验与正式购买链路
- 订单详情与后台分析口径

要做的事：

1. 定义优惠快照结构：
   - 券标识
   - 券版本
   - 当时规则
   - 实际折扣金额
   - 实付金额
2. 明确“已使用券规则变更”的策略：
   - 原券冻结关键规则
   - 或复制新版本券
3. 明确订单、分析、客服三方统一读取哪份真相

验收标准：

- 任意订单都能回看当时优惠规则
- 优惠券详情页和分析页不再受后续配置修改污染

## `DV2-0-3` 退款回滚口径统一

目标：

- 统一退款后优惠券对“次数、额度、报表”的影响解释

涉及范围：

- 商城退款
- 优惠券次数回补
- 经营报表净值口径

要做的事：

1. 明确退款类型：
   - 全额退款
   - 部分退款
   - 售后撤销
   - 风控撤单
2. 明确回滚对象：
   - 总可用次数
   - 每用户使用额度
   - 用户资产返还
   - 经营报表净值
3. 明确后台与客服的话术口径

验收标准：

- 同一笔退款在运营、客服、财务视角下解释一致
- 报表能区分毛口径和净口径

## `DV2-0-4` 风控恢复闭环与观察期策略

目标：

- 让风险自动停用不再是单行道

涉及范围：

- 风控自动响应
- 恢复审批
- 观察期策略
- case 联动

要做的事：

1. 明确恢复方式：
   - 人工恢复
   - 观察期恢复
   - 自动恢复
2. 定义恢复前置条件：
   - 是否需要复核最近订单
   - 是否需要关闭 case
   - 是否需要观察期
3. 定义恢复后的状态：
   - 直接恢复可用
   - 进入观察期
   - 继续停用

验收标准：

- 风险停用后的券存在明确恢复路径
- 恢复操作能沉淀结构化结论
- 批量恢复不再只是“重新打开开关”

## 8. 不建议当前就做的事

以下内容建议明确后置，避免抢跑：

- 在 P0 未完成前就上多券叠加
- 在没有历史快照前就上 ROI 大盘

- 在没有资产模型前就把结算页改成纯卡券模式
- 在产品语义未收口前就强行统一 `discount_codes` 与 `redemption_codes` 底层表

## 9. 最终建议

这套升级最关键的判断不是“功能多不多”，而是顺序对不对：

- `P0` 做可信性
- `P1` 做增长性
- `P2` 做平台性

只要这个顺序不乱，现有优惠券 V1 可以非常自然地演进成一个完整的营销资产系统；如果顺序乱了，就很容易变成“前台更花哨，但后台口径更混乱”。
