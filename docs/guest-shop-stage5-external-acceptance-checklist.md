# Task 2.1 阶段 5 外部验收清单（点击级操作版）

日期：2026-09-28

本清单用于隔离环境、Admin Studio、真实设备和支付提供方验收。每一项都要记录：环境、操作者、北京时间、非敏感订单号或 provider reference、页面结果和目标库回读结果。不得记录卡密、claim token、恢复码、密钥、webhook URL 或完整敏感地址。

**安全前提：** Codex 不执行 SQL、不代付款、不打开游客商品/SKU/促销/多件开关、不部署。需要数据库检查时，由操作者执行另行提供的只读 SQL。没有真实操作证据的适用项目保持 `待外部证据`；明确关闭、无批准资源或用户确认不需要的项目记 `N/A`，不能把它们永久留在待办，也不能仅凭代码测试标 PASS。

## 0.1 适用性分流

每个项目开始前先判断：能力已启用且有批准隔离资源才执行；能力关闭、没有批准的 provider/设备/异常样本或用户确认不需要时，记录原因、负责人和重新适用的触发条件并记 `N/A`；页面应可用但按钮缺失、接口报错或状态不一致时记 `FAIL/BLOCKED`。以后启用能力或出现对应资源时，只重新打开该项目。

本版流程适配：付款方式按钮直接完成订单创建，没有单独的「创建支付订单」按钮；数量、闪购和阶梯价检查通过打开「立即购买」后的确认订单弹窗自动重新报价，没有独立的「预览」按钮。邮箱和查询密码按隔离商品当前字段标记决定是否填写，字段缺失或可选不构成失败；游客「订单查询」应保持游客入口，不应被重定向到登录钱包页。取消未付款订单后应立即释放库存，再次购买应创建新订单。

## A. Admin Studio 游客异常订单与审计

### A1. 打开入口和权限

**前置条件：** 使用隔离环境、具有 `shop.manage` 的管理员账号；准备一笔可回滚的异常订单或确认当前无数据。

1. 浏览器打开 `/admin-studio.html`。
2. 登录管理员账号。
3. 左侧点击「商城」。
4. 点击「游客异常订单」。
5. 等待「游客促销安全状态」和「游客异常订单」区域加载。

**预期：** 页面正常打开；没有权限时明确显示拒绝，不显示半旧数据；安全面板包含 breaker、CN/INTL 预算、最近安全事件等只读信息。

### A2. 验证异常筛选、站点、通道和空结果

1. 找到下拉框「异常订单」(`#guestExceptionFilter`)。
2. 依次选择「全部扫描结果」「已付款未发货」「预占超时」「支付待复核」「支付失败」「金额不匹配」「退款异常」「库存不一致」「履约死信」。每次都点击「查询」。
3. 找到「全部通道」(`#guestExceptionProvider`)，依次选择「ZPay」「NOWPayments」，每次点击「查询」。
4. 使用站点筛选（如页面提供）选择 CN、INTL，各点击「查询」。
5. 清空筛选后查询一次。

**预期：** 表格只显示符合条件的记录；未知条件或无记录时显示空结果/零计数，不报错、不保留上一筛选的旧数据；分页和刷新不改变筛选语义。

**失败证据：** 记录筛选值、时间、页面错误码和结果行数，不复制支付密钥或卡密。

### A3. 按订单号查询

1. 在 `#guestExceptionQueryInput`（placeholder「按游客订单号筛选」）输入隔离订单号。
2. 点击「查询」。
3. 再输入不存在的订单号并查询。

**预期：** 第一次只显示目标订单；第二次显示空结果；不会把相似订单混入。

### A4. 申请退款（仅隔离、已付款未发货订单）

**状态：PASS / 已完成（2026-09-24）**

**证据：** provider 后台退款成功；本地订单可同步为 `refund_status=succeeded`、`payment_status=refunded`；provider 退款交易号可写回，退款错误码/错误信息可清除；reservation 与促销台账回读符合释放结果；退款后查询 provider 最终状态的 worker 修复及 Admin Studio「已退款」分类测试通过。

1. 在目标行点击「申请退款」。
2. 在弹窗 `#guestExceptionOpsReason` 输入不少于 8 个字，例如「隔离沙箱退款回读演练」。
3. 点击确认按钮；不要重复点击。
4. 等待成功提示和队列刷新。
5. 再查询该订单，记录 refund、reservation、促销台账和审计状态。
6. 使用同一操作重试一次，验证幂等结果。

**预期：** 原因校验生效；成功后进入预期的 `pending`/`manual_review` 状态；库存和促销预占按合同释放；重复提交不会重复退款或重复返还；后台列表不显示卡密/claim token。

**说明：** 本条验收已完成；生产环境中的代码生效仍以按发布流程合并部署后的回读为准。

### A5. 补发库存（代码/隔离验证通过；真实异常样本不作为门槛）

A5 已通过代码合同测试和隔离故障夹具验证。正常库存流程不会为了测试制造真实 `paid_unfulfillable` 订单；生产中只有业务逻辑自然产生该状态时才执行以下运营操作。

1. 在目标行点击「补发库存」。
2. 输入不少于 8 个字的原因。
3. 点击确认，等待队列刷新。
4. 回读订单履约、reservation 和库存状态。

**预期：** 从同 SKU 非共享库存领取 1 张并进入 `delivered` 或明确的人工状态；失败时进入可审计状态；不显示卡密；非 quantity=1 或非指定异常状态应拒绝操作。

### A6. 解锁履约死信

1. 先确认目标订单没有活动租约。
2. 在死信行点击「解锁死信」。
3. 填写不少于 8 个字的处理原因。
4. 点击确认。
5. 回读任务状态和审计事件。

**预期：** 仅对应死信被清除，任务进入可重试/重排队状态；没有活动租约时才允许；重复解锁幂等；其他订单不受影响。

### A7. 刷新游客促销安全状态

1. 点击「刷新状态」。
2. 记录 breaker、CN/INTL 预算、最近安全事件的时间戳和非敏感摘要。
3. 重复刷新一次。

**预期：** 面板只读，没有控制 breaker/预算的写入按钮；目标库缺行、权限错误或查询失败时整体显示不可用/错误，不展示半旧数据；两次刷新不会产生写入事件。

## B. 告警送达与恢复

### B1. 确认渠道

1. 在 Admin Studio 左侧点击「设置」。
2. 打开「运营告警」区域。
3. 确认实际启用的渠道（Telegram、Feishu、email 等）和责任人。
4. 不要在截图、聊天或记录中复制 token、webhook URL 或完整收件地址。

**预期：** 至少有一个允许测试的真实接收渠道；当前 Telegram、飞书、邮件均已启用时，三条都记录为启用。某渠道有意关闭且不在本轮范围时记 `N/A`，不要求反复等待它变成 PASS。

### B2. 测试发送

1. 点击对应渠道「测试发送」或「自检」。
2. 选择允许测试的模板。
3. 点击发送并等待页面结果。
4. 在接收端确认消息到达。
5. 记录非敏感 message ID、接收时间和接收人。

**预期：** 页面和接收端都显示成功；失败时页面有可追踪错误；不会把密钥回显到页面或日志。

### B3. 事件去重与恢复

1. 使用隔离样本触发一次 `paid_unfulfilled`、`refund_pending`、delivery failure/dead-letter 或 promo budget/breaker 告警。
2. 确认首条告警到达并记录 message ID。
3. 在不改变事件身份的情况下重复 sweep/重试一次。
4. 修复隔离样本状态。
5. 再执行一次 sweep。

**预期：** 同一事件只发一次告警；状态恢复只发一次 recovery；重复 sweep 不重复通知；记录责任人和 SLA。

## C. 真实设备与无障碍

每台设备都使用隔离商品；支付可停留在未付款状态，不要付款。

### C1. iOS Safari 和 Android Chrome

1. 在手机浏览器打开商城页面，切换到游客状态。
2. 选择隔离游客商品，点击「立即购买」。
3. 按页面字段标记填写邮箱和查询密码（仅在当前隔离商品要求时填写），选择支付方式，检查 quote 和订单状态。
4. 分别在竖屏和横屏重复打开/关闭弹窗。
5. 使用系统返回、刷新，再从订单查询页恢复。

**预期：** 弹窗不被键盘遮挡；步骤、焦点、金额和订单状态不丢失；关闭后焦点回到触发按钮；支付回跳或刷新后可恢复到正确状态。

### C2. 桌面键盘与缩放

1. 在 Chrome/Firefox/Safari 打开游客购买弹窗。
2. 只使用 Tab/Shift+Tab 遍历控件。
3. 检查焦点始终留在 dialog 内且顺序合理。
4. 按 Escape 关闭弹窗，再次打开。
5. 设置浏览器缩放 200%，重复一次。

**预期：** `role=dialog`、标题和错误提示可被辅助技术关联；焦点不逃逸；Escape 可关闭；200% 缩放下没有不可操作的遮挡或横向截断。

### C3. 读屏

当前产品没有读屏器功能，且本轮没有读屏需求。按用户确认记 `N/A`，不作为阶段 5 门槛；以后若新增读屏需求，再建立独立的读屏验收项目。

### C4. 弱网、多标签和隐私模式

1. 使用浏览器网络节流模拟慢网，打开 quote 和创建订单。
2. 在两个标签页分别打开同一商品，改变其中一个 quote 后提交。
3. 在隐私/无痕窗口重复打开订单查询页。

**预期：** 超时有可理解错误和重试入口；quote 变化触发重新确认；多标签不会错误复用旧金额；隐私模式不泄漏前一会话订单。

## D. 多件隔离证据

**前置条件：** 仅使用隔离商品、隔离库存和隔离数据库；当前隔离商品为「D1-多件原子预占-测试 / D1-成功路径」，商品和 SKU 上限至少为 3，且有至少 3 张非共享可用库存。生产运行时 `GUEST_SHOP_MAX_QUANTITY` 继续为 1。若购买弹窗没有「购买数量」字段，先核对隔离商品配置；前置条件未满足时记 `N/A`，不把隐藏控件当成失败。

### D1. 数量和原子预占

1. 在商城找到隔离商品，点击商品详情中的「立即购买」。
2. 在「确认订单」弹窗确认出现「购买数量」，点击 `+` 一次使数量变为 2；数量变化会自动重新报价，当前没有单独的「预览」按钮。
3. 选择付款方式创建订单，看到订单号后停止，不要扫码或转账。
4. 只读回读 reservation 行数、库存 available 和订单数量；随后点击「取消订单」，确认库存释放，再回读一次。

**预期：** 服务端决定数量和金额；一次事务生成 N 个 reservation；库存不足时整笔失败，不留下部分 reservation，库存和预算不变。

### D2. 逐卡履约

1. 只有在批准的最小支付金额、provider 和隔离库存均已准备时，对 quantity=2 订单完成合法支付；否则本项记 `N/A`。
2. 让 worker 执行一次履约。
3. 回读 consumed reservation 数量和订单 fulfillment 状态。

**预期：** 每张卡单独 claim；所有 reservation consumed 后才进入 `delivered`；不出现部分 delivered 或重复 claim。

### D3. 释放、失败和租约恢复

按 provider、死信/租约样本和退款余额的适用性，分别对独立订单执行；不具备条件的分支记 `N/A`：

1. 到期：不付款，等 TTL 后回读。
2. 支付失败：使用提供方的失败回调/测试事件。
3. 退款：使用 Admin Studio 退款流程。
4. worker 重启/租约恢复：在隔离 worker 环境重启或让租约超时后再运行一次。

**预期：** 每种故障都释放全部 reservation；库存回到 available；促销额度和预算返还；没有 stale hold、部分 reservation 或重复履约。每次都记录订单号、时间和回读结果。

## E. 闪购、阶梯价与促销组合

**前置条件：** 使用隔离 CN 商品、隔离 SKU 和测试促销码；确认服务端时间和目标库预算足够；不要使用生产商品。闪购/阶梯价/促销 fixture 未批准或能力关闭时，E1-E4 记 `N/A`，不为凑样本创建订单。

### E1. 开始前

1. 在 Admin Studio 商品编辑页打开隔离商品。
2. 设置阶梯价区间和闪购开始时间为未来时间，保存。
3. 在促销配置中确认测试码适用站点、折扣比例、游客额度和有效期。
4. 回到游客 checkout，选择该 SKU 并点击「立即购买」；在确认订单弹窗等待自动报价，当前没有单独的「预览」按钮。

**预期：** 闪购尚未开始时使用阶梯价或原价；促销只在符合条件时计算；quote 显示服务端金额。

### E2. 进行中

1. 等到服务端时间进入闪购窗口。
2. 刷新商品页和 checkout，重新获取 quote。
3. 记录 list amount、flash price、discount、net amount 和 payable。

**预期：** 使用闪购价作为折扣前基准，再按规则计算促销；客户端篡改金额不会被接受；库存/预算预占与 quote 一致。

### E3. 结束后

1. 等到结束时间之后刷新 checkout。
2. 再次获取 quote，不复用旧 quote。
3. 回读订单/价格快照。

**预期：** 闪购价失效，回退到有效阶梯价/原价；旧 quote 提交被拒绝或要求重新确认。

### E4. 边界和释放

1. 在开始前、开始后、结束前和结束后分别打开隔离商品详情，点击「立即购买」，在确认订单弹窗等待自动报价完成并记录结果；结束后必须重新打开弹窗，不提交旧报价。
2. 对一个隔离订单保持未付款直至 TTL 到期。
3. 回读促销 redemption、reservation、库存和预算。

**预期：** 边界由服务端时钟决定且结果稳定；到期后 reservation、促销额度和预算全部返还；没有重复台账或 stale hold。

## F. INTL/NOWPayments

**前置条件：** 使用已批准的隔离 INTL 商品和最小测试金额；确认提供方测试网络/账户、回调 URL 和人工退款责任人已准备。不得把密钥或完整地址写入记录。任一条件缺失时 F1-F4 记 `N/A（INTL/provider 未批准）`，不要求打开国际游客商品。

### F1. 进入国际站

1. 打开国际站 URL，并确认站点参数为 `site=intl`。
2. 退出登录，进入游客购买流程。
3. 选择批准的隔离 INTL SKU。
4. 检查支付方式列表。

**预期：** 只显示已批准的 INTL 支付渠道（例如 NOWPayments/USDT-BEP20）；CN 渠道不会错误出现在 INTL 流程。

### F2. Quote 和 provider order

1. 点击「立即购买」并记录 quote 展示的结算基准、provider quote 币种、报价有效期和应付金额。
2. 点击已选付款方式创建 provider order；当前没有独立的「创建支付订单」按钮。
3. 只记录 provider order reference 和时间，不记录密钥、完整地址或回调签名。

**预期：** 订单结算基准仍是 CNY；provider quote 可以是 USD/USDT；provider reference 与内部订单一一绑定；金额由服务端生成。

### F3. 合法支付与 webhook

没有批准的最小金额、真实 webhook 或 provider 测试能力时记 `N/A（provider 未批准）`，不得用 mock 代替。

1. 使用最小批准测试金额完成支付。
2. 等待真实合法 webhook 到达。
3. 在 Admin Studio 或只读回读中确认实际到账金额和币种。
4. 观察支付确认、reservation 和履约状态。
5. 重放同一 webhook 一次。

**预期：** 只有签名正确、provider order 匹配、`actually_paid` 和 `actually_paid_currency` 精确符合的 webhook 才确认支付并发货；重复 webhook 幂等，不重复发货。

### F4. 错误支付与退款

没有 provider 测试能力、退款余额或人工复核责任人时记 `N/A`；只有具备可回读错误事件和退款回执时才执行。

1. 使用提供方测试能力发送少付、错币种、未绑定订单或错误签名事件。
2. 观察订单状态和异常队列。
3. 在 Admin Studio → 商城 → 游客异常订单打开该订单。
4. 对 NOWPayments 退款按「申请退款」流程填写原因并确认。

**预期：** 错误事件进入 `review`/异常状态，不确认、不发货、不释放错误库存；退款需要人工复核时保留人工状态和审计事件，不伪造自动成功。

## G. 通过/失败判定与归档

### G1. 单项 PASS 条件

一项只有同时满足以下条件才能标 PASS：

1. 页面操作完成，按钮/字段行为与本清单一致；
2. 目标库或 provider 回读与预期一致；
3. 没有未解释的订单、reservation、预算、促销台账、告警或死信残留；
4. 证据不含卡密、claim token、恢复码、支付密钥或完整敏感地址；
5. 失败重试、幂等和恢复路径已记录（适用时）。

### G2. 失败记录

失败时记录：步骤编号、北京时间、环境、脱敏订单号/provider reference、页面错误文案/错误码、目标库只读回读摘要和复现步骤。不要为了让结果 PASS 而修改生产数据或绕过安全闸。

### G3. 阶段收口

全部适用项达到 PASS，或明确标记 N/A 并由负责人确认原因、负责人和重新适用触发条件后，才能更新阶段 5 为完成。A5 的真实 `paid_unfulfillable` 外部样本已明确标记 N/A，不再作为上线门槛；C3 读屏按需求记 N/A；INTL/provider 未批准时 F1-F4 不阻塞 CN 收口。能力启用或资源批准后，只重新打开对应项目。
