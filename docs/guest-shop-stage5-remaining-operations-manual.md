# 阶段 5 未完成验收操作手册

日期：2026-09-28

本文记录阶段 5 中仍需收口的 A6 至 G3，以及 A5 的代码/隔离验证结论。A1、A2、A3、A4 已完成，不在本文重复列为待办。本版已按当前商城页面、游客订单查询、告警渠道、数量开关和支付流程更新；旧版中不存在的按钮、已取消的能力和已完成的项目不再作为验收门槛。

## 使用边界

- 只使用隔离环境、隔离商品、隔离 SKU、隔离库存和隔离促销码。
- 不使用生产商品制造故障。
- 不为了制造异常而付款、重复退款或手工修改正常订单状态。
- 不记录卡密、claim token、恢复码、支付密钥、webhook URL 或完整敏感地址。
- 每一项都记录环境、北京时间、脱敏订单号/provider reference、页面结果、目标库或 provider 回读结果和结论。
- 代码测试通过不等于外部验收通过；真实页面、目标库、告警或支付证据缺失时保持 `待样本`、`待外部证据` 或 `N/A`。

## 本版相对旧手册的适配

本版以当前 checkout 和 Admin Studio 为准。旧手册中的“单独创建支付订单”按钮已并入各付款方式按钮；点击付款方式会先重新确认报价，再创建订单。数量变化会自动重新报价，页面没有独立的“预览”按钮；涉及时间边界的报价检查也必须通过打开「立即购买」后的确认订单弹窗完成。未付款订单点击「取消订单」会立即释放预占，之后再次点击商品应创建新订单，不得把上一笔已取消或已发货订单当作新测试样本。

邮箱和查询密码是否必填，以当前隔离商品在确认订单弹窗中的字段标记和服务端配置为准：字段不存在或标记为可选时不应判失败；只有页面标记必填却无法填写、提交后服务端拒绝或恢复流程不一致时才记 `FAIL/BLOCKED`。游客商城的「订单查询」按游客入口验证，不跳转到登录钱包页面。

闪购、阶梯价、促销组合、INTL/NOWPayments、读屏和真实异常订单都先走适用性分流。能力关闭、没有批准资源或用户明确不纳入本轮时记 `N/A`，并写清重新适用触发条件；页面或接口按设计应可用却缺失时仍记 `FAIL/BLOCKED`。

## 适用性分流（每项开始前先做）

阶段 5 的项目不是无条件逐项强行执行。每个项目先按以下顺序判断，避免把关闭的功能或不存在的测试资源变成永久失败：

1. **能力已启用且有批准的隔离资源**：执行本项目的点按步骤；页面、目标库/provider 回读和残留检查都满足后记 `PASS`。
2. **能力明确关闭、用户已确认不需要，或没有批准的 provider/设备/异常样本**：记 `N/A`，同时填写原因、负责人和重新适用的触发条件。`N/A` 不计为失败，也不要求制造订单、付款或故障来“凑样本”。
3. **能力应该可用但页面缺失、按钮不可用、接口报错或状态不一致**：记 `FAIL` 或 `BLOCKED`，保留错误码和复现步骤，不能用 `N/A` 掩盖实现问题。
4. **代码合同已经覆盖、而真实异常按业务语义不会自然出现**：可按代码/隔离夹具结论记 `PASS`，并把真实样本记为 `N/A`，例如 A5、A6。

只有第 2 类项目可在阶段收口时按 `N/A` 关闭；以后启用能力、批准 provider、出现真实样本或新增设备时，按触发条件重新打开对应项目。

## A5：补发库存

### 当前结论

A5 的真实外部补发闭环不作为阶段 5 上线门槛。正常库存语义下，库存为 1 时，未付款订单会持有该库存，其他买家不能购买；付款后应使用该预占库存发货。`paid_unfulfillable` 只应由支付已确认但履约阶段出现受控异常时自然产生，不能通过手工改状态或破坏正常订单制造。

A5 已通过前端按钮条件、权限、二次确认、后端拒绝路径、原子补发、审计和不泄露敏感信息的自动化合同测试；本地 `paid_unfulfillable` fixture 仅用于隔离界面/拒绝路径，不创建真实订单。

```text
A5：PASS（代码合同测试 + 隔离故障夹具）
真实 paid_unfulfillable 外部样本：N/A，不作为上线门槛
```

### 页面操作

1. 浏览器打开 `http://localhost:8000/admin-studio.html`。
2. 左侧点击「商城系统」。
3. 点击商城顶部「游客异常」。
4. 在「异常订单」下拉框选择「已付款未发货」。
5. 点击「查询」。
6. 找到目标订单行。
7. 在该行最右侧「操作」列寻找箱子图标。
8. 鼠标悬停，确认提示为「补发库存」。
9. 点击箱子图标。
10. 在处理原因框输入不少于 8 个字，例如：`隔离订单人工补发库存验证`。
11. 点击「确认补发」。
12. 等待成功提示和列表刷新。
13. 重新按订单号查询该订单。
14. 回读订单履约、reservation、库存和审计状态。

### 预期结果

- 从同 SKU 的可用非共享库存领取 1 张。
- 订单进入 `delivered` 或明确的人工处理状态。
- reservation 进入合同规定的最终状态。
- 库存只减少 1 张。
- 不返回或显示卡密、claim token。
- 重复提交不会重复扣库存或重复发货。

### A5 判定

A5 按代码合同测试与隔离故障夹具结果标记 PASS。生产或目标库自然产生 `paid_unfulfillable` 时，运营才按页面步骤执行补发；不得为了验收创建真实扣款或手工篡改订单。

## A6：解锁履约死信

### 当前前置条件

需要一笔隔离订单，其 `fulfillment_status = dead_letter`，并确认没有活动履约租约。

### 页面操作

1. 打开 Admin Studio。
2. 左侧点击「商城系统」。
3. 点击商城顶部「API 履约」。
4. 在任务筛选中选择「死信」或「履约死信」。
5. 找到目标订单。
6. 确认该行没有活动租约。
7. 点击该行右侧「解锁死信」。
8. 输入不少于 8 个字，例如：`隔离死信订单恢复队列验证`。
9. 点击「确认解锁」。
10. 等待列表刷新。
11. 回读任务状态和审计事件。
12. 对同一订单重复执行一次，验证幂等。

### 预期结果

- 只有目标死信被清除。
- 任务进入可重试或重新排队状态。
- 有活动租约时拒绝操作。
- 重复解锁不重复创建任务。
- 其他订单不受影响。
- 写入可追踪审计事件。

## B3：告警去重和恢复

### 需要的隔离样本

任选一个隔离事件：`paid_unfulfilled`、`refund_pending`、delivery failure/dead-letter 或 promo budget/breaker。

### 操作步骤

1. 使用隔离样本触发一次告警。
2. 等待首条告警到达并记录 message ID。
3. 在不改变事件身份的情况下重复一次 sweep 或重试。
4. 确认没有重复告警。
5. 修复隔离样本状态。
6. 再执行一次 sweep。
7. 确认只产生一条 recovery 消息。

### 预期结果

同一事件只发送一次；恢复只发送一次；重复 sweep 不重复通知；责任人和处理时间可追踪。

当前记录：B1、B2、B3 已由操作者完成渠道确认、测试推送接收和去重/恢复验证；后续只在路由、模板、接收端或告警实现发生变化时重开。

## D1：数量和原子预占

### 前置条件

仅使用隔离商品、隔离库存和隔离数据库。当前已核验的隔离商品为「D1-多件原子预占-测试 / D1-成功路径」，商品和 SKU 的游客上限均至少为 3，并且有至少 3 张非共享可用库存。生产运行时 `GUEST_SHOP_MAX_QUANTITY` 继续为 1；不要用生产商品替代该隔离商品。

如果打开游客购买弹窗后没有出现「购买数量」字段，先回到 Admin Studio 核对商品上限、SKU 上限和库存；前置条件未满足时记 `N/A（隔离多件能力未启用）`，不要把隐藏控件当成页面失败，也不要修改生产开关。

### 操作步骤

1. 打开本地或批准的隔离商城，找到「D1-多件原子预占-测试」，点击商品卡进入详情，再点击「立即购买」。
2. 在「确认订单」弹窗等待商品信息加载；确认出现「购买数量」和 `+` 按钮。
3. 点击 `+` 一次，使数量从 1 变为 2；等待页面提示重新报价结束，记录页面显示的数量、商品金额、优惠和应付金额。这里没有单独的「预览」按钮，数量变更会自动重新调用 preview。
4. 选择一个可用付款方式。当前流程会在点击付款方式时创建订单；看到订单号后立即停止，不要扫码或转账。
5. 在订单仍处于未付款/预占状态时记录订单号并做只读回读：订单数量应为 2，reservation 应为 2 行，库存可用数应减少 2。
6. 点击「取消订单」，确认弹窗提示订单已取消、库存已释放；再次只读回读 reservation、库存和订单状态。
7. 若要验证库存不足分支，只使用预先批准的“库存少于请求数量”隔离 SKU；没有此 fixture 时记 `N/A`，禁止手工扣库存或制造半成功订单。

### 预期结果

服务端决定数量和金额；数量 N 产生 N 个 reservation；取消后整组释放；库存不足时整笔失败，不留下部分 reservation，库存和预算不变。点击付款方式即创建订单，不能再按旧手册寻找「创建支付订单」按钮。

## D2：逐卡履约

### 适用条件

只有在存在批准的最小支付金额、已批准的支付渠道和可回滚的隔离库存时执行。没有批准 provider 或本轮明确禁止付款时记 `N/A`，不要用模拟成功状态代替真实履约。

### 操作步骤

1. 使用 D1 的 quantity=2 隔离订单。
2. 完成合法隔离支付。
3. 让 worker 执行一次履约。
4. 回读 reservation 状态和订单履约状态。

### 预期结果

每张卡单独 claim；所有 reservation consumed 后才进入 `delivered`；不出现部分 delivered 或重复 claim。

## D3：释放、失败和租约恢复

分别准备适用分支的独立隔离订单。某一分支没有批准的 provider、死信样本或退款余额时，只关闭该分支为 `N/A`，不影响其他分支：

### D3-1 到期释放

1. 创建订单。
2. 不付款。
3. 等待 TTL 到期。
4. 重新查询订单。
5. 回读 reservation 和库存。

预期：reservation released，库存回到 available。

### D3-2 支付失败

1. 使用提供方测试失败事件。
2. 确认订单没有进入 confirmed。
3. 回读库存和 reservation。

预期：不发货，库存正确释放或保持合同规定状态。

### D3-3 退款

只有 provider 退款能力、余额和人工复核责任人已批准时执行；否则记 `N/A（退款 provider/余额未批准）`，不能因为 provider 余额不足反复点击退款。

1. 使用隔离已付款订单。
2. Admin Studio → 商城系统 → 游客异常。
3. 查询目标订单。
4. 点击「申请退款」。
5. 输入至少 8 个字原因。
6. 点击确认。
7. 回读 refund、reservation、促销台账和审计状态。

预期：退款状态、库存释放、促销台账和审计一致；重复操作幂等。

### D3-4 worker 恢复

1. 在隔离 worker 环境使履约任务进入恢复条件。
2. 让租约超时。
3. 再运行一次 worker。
4. 回读订单、reservation 和库存。

预期：没有 stale hold、重复履约或部分 reservation。
