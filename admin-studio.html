上线前验收清单

1. 先确认迁移和策略已生效 完成并核对 20260321_add_shop_delivery_conflict_controls.sql 与 20260321_add_shop_delivery_global_reservations.sql。
通过标准：履约策略页可正常读取和保存目标 / 通道并发、最小间隔、冲突回退和冲突死信阈值；后台日志没有 reservation / conflict RPC 缺失报错。
2. 走通一条成功履约链路 用测试商品下 1 笔 API 履约单，确认任务从 pending 进入 processing 并最终到 delivered。
通过标准：主任务表、人工重放记录、全局占位观测都能看到完整闭环，任务完成后不残留 reservation。
3. 走通一条异常和人工处理链路 至少演练 1 次超时 / 上游失败 / 锁漂移场景，确认会进入 retry_waiting、冲突审计或死信，并能用 requeue、replay、force unlock 拉回。
通过标准：每个动作都有对应审计或状态流转，不出现“点了但无记录”。
4. 验收观测与联动排障入口 分别点击热点、趋势柱、冲突审计、死信和占位面板，确认能联动筛选、滚动定位、高亮任务，并能用面包屑单项移除。
通过标准：恢复链接刷新后仍能回到原视角，运营无需手动重新拼筛选条件。
5. 先灰度，再放大并发 正式上线先用单实例 / 低并发，观察 24 小时冲突、死信和 token / worker 漂移；确认稳定后再提高 worker_parallelism 或扩成多实例。
通过标准：没有持续上涨的冲突热点，也没有长时间卡在 processing 的任务。

运营 SOP

1. 每日巡检顺序 先看顶部 summary，再看近 24 小时冲突趋势和热点，最后处理死信、锁冲突、全局占位。
优先级：processing 卡住 / 锁漂移 > 冲突死信 > 普通重试等待。
2. 标准排障路径 从热点或趋势下钻，点进冲突审计锁定上下文，再回到主任务表确认订单、目标、通道和最近错误。
原则：先定位是不是单一目标 / 通道热点，再决定是配置问题、上游抖动还是锁状态异常。
3. 动作选择规则 requeue：配置刚修好、上游短暂抖动后重新入队。
replay：需要立刻再跑一次，且已确认下游幂等安全。
force unlock：只在确认是 stale lock、token drift、worker drift 时使用。
mark dead letter：目标无效、下游长期不可用，或冲突已达到人工止损阈值。
4. 升级给研发的条件 15 分钟内同一目标 / 通道持续冲突放大、出现大面积 token / worker 漂移、同类任务批量卡在 processing，或人工重放后仍重复失败。
升级时：附上恢复链接、订单号、热点目标 / 通道和最近审计记录。
5. 交接和回溯方式 排障过程中随时用顶部“复制恢复链接”保存上下文；交班时把链接和结论一并发给下一位处理人。
目标：让对方打开页面就能回到同一任务、同一时间桶和同一组热点，不需要口头重建现场。
推荐上线节奏：先应用迁移，再部署 server 和后台，先灰度观察，再逐步放大并发。如果是首次把这套界面交给运营，建议先按上面的清单走一轮演练，把 requeue、replay、force unlock 三个动作都实际点通一次。

支付总览

总订单 当前时间范围内纳入统计的支付订单总数。
异常时：数量突然断崖式下降。
先查：时间范围、站点筛选、支付通道是否切换。
处理：先切回最近 7 天和全站点，再核对最近订单是否仍在持续写入。
支付成功率 paid + redeemed 占总订单的比例，用来看支付链路是否稳定。
异常时：成功率突然下降。
先查：失败订单、签名异常、金额不匹配、通道配置。
处理：优先看异常运维里的失败订单，再核对当前通道密钥、金额映射和回调地址。
意图匹配率 支付意图 payment_checkout_sessions 成功关联到最终订单的比例，越高越健康。
异常时：匹配率长期偏低或突然掉到 0。
先查：最近新单是否写入 session、最近订单里的意图匹配状态。
处理：先确认新单不是历史订单，再检查 create 入口、回调回填和认领兜底是否正常。
支付金额 当前范围内已支付订单的累计金额。
异常时：金额和实际收款感知不一致。
先查：是否只统计了某个时间段、某个站点或某个通道。
处理：先看最近订单金额汇总，再对照通道表现和全站收支里的充值收入。

全站收支

充值收入 所有充值订单实际入账金额。
异常时：收入增长但用户积分没变化。
先查：支付成功后是否已认领、是否存在未认领订单。
处理：去异常运维检查“已支付但未认领”，必要时引导用户查码或后台补认领。
商城消耗 商城订单累计消耗的积分，不等同于支付收入。
异常时：消耗异常偏高或偏低。
先查：商城订单量、退款量、活动赠送和模拟支付。
处理：结合积分流水分类看“商城消费”一项是否突然放大，再核对商城订单和退款。
流入 / 流出 / 净流动 按积分维度看全站流动情况，用来判断库存、赠送和消费是否失衡。
异常时：净流动持续为负或波动过大。
先查：奖励/返佣、商城消费、验证消耗、内容解锁。
处理：在积分流水分类中定位放大量最大的类别，再回到对应业务模块核对。
当前流通余额 当前仍在用户账户中流通的积分总量。
异常时：余额突然拉高或快速下降。
先查：充值收入、奖励发放、商城消耗和后台手工发放。
处理：优先比对“付费”和“奖励”占比，再核对最近的大额积分变动。

意图匹配状态

自动回填 支付回调阶段已自动把支付意图关联到最终订单，这是最理想状态。
异常时：自动回填占比突然下降。
先查：回调是否到达、provider_order_no 是否正常写入。
处理：优先排查回调链路和意图匹配率，再看是否大量退化成认领兜底。
认领兜底 回调阶段没完成关联，后续由钱包查码 / 认领阶段补上。
异常时：兜底比例明显偏高。
先查：回调自动回填是否失效、session 是否未及时关联。
处理：说明用户能补回，但自动闭环偏弱，应优先修回调或意图回填。
待回填 支付意图已创建，但还没有挂到最终订单。
异常时：长时间停留在待回填。
先查：用户是否已完成支付、回调是否到达、是否已认领。
处理：先等短时间同步；若超时仍存在，检查 webhook、支付通道回传和认领流程。
意图失败 支付意图本身失败、取消或过期。
异常时：这一类突然变多。
先查：支付页能否正常拉起、用户是否中途取消、通道是否失效。
处理：先检查当前支付通道配置和拉起地址，必要时切回 mock 或备用通道。
历史订单 这笔单创建时还没启用支付意图层，所以不参与意图匹配率。
注意：它不是异常。
处理：主要用于识别老单，不需要专门补数据，除非你要做历史迁移。

异常运维

订单待审核 套餐匹配、金额或签名需要人工确认。
先查：金额、套餐映射、通道来源、回调原文。
处理：金额对得上就补通过；金额对不上或来源异常就保持拦截并继续核查。
签名 / 金额异常 优先检查支付通道密钥、回调签名算法和回调来源地址。
先查：密钥是否更新、金额是否与套餐一致、是否存在伪造回调。
处理：签名失败先核密钥；金额不匹配先核套餐配置，再决定忽略或人工处理。
已支付但未认领 提醒用户到钱包输入订单号；必要时后台人工补认领。
先查：订单是否已支付成功、兑换码是否已生成、用户是否已登录。
处理：优先引导用户自己认领；若长时间挂起，再后台人工补认领。
重复回调 重点看是否重复写单、重复发货。
先查：是否只是重复通知、还是已造成重复入账。
处理：确认幂等键是否生效；若只是重复通知可忽略，若已写脏数据需人工回滚或标记处理。

通道表现与清理

通道表现 对比各支付通道的订单量、成功率、认领率和意图匹配率。
异常时：某个通道成功率或匹配率显著低于其它通道。
处理：优先切到该通道卡片排查配置、拉起地址、回调质量和近期错误类型。
最近订单 适合人工核对支付结果、认领时间、站点和意图匹配状态。
先查：订单号、金额、状态、意图匹配、认领时间。
处理：发现异常时，把这张表当作第一现场，先确认是支付失败、回填失败还是认领失败。
测试数据清理 只针对 AUTO_CDX_ / SMOKE_ 测试订单和测试账号，不会影响正式订单。
显示：只有扫描到待清理测试数据时才出现。
处理：上线前或联调结束后执行一次，避免测试数据污染总览和通道表现。
建议优先处理顺序：意图失败 / 已完成但未回填 / 金额或签名异常 / 已支付但未认领。如果是大面积成功率下降，先查 通道配置 和 回调链路；如果是局部异常，先从 最近订单 定位问题类型。
